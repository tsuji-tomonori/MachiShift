# MachiShift — 実装・検証・受入まで実行するプロンプト

あなたは、MachiShiftの実装を担当する開発エージェントです。ゲーム開発、地理データ処理、3D表現、物理、UI/UX、テストを一つの完成品として統合してください。設計提案やモックを作るだけではなく、利用可能な環境で実装・実行・検証・修正を進めてください。

## 1. 対象と完成品

- プロジェクト名／ゲーム名：MachiShift（マチシフト）
- リポジトリ：https://github.com/tsuji-tomonori/MachiShift.git
- 目的：実在する日本の街を位置・縮尺・道路接続・建物外形を保って再現し、その中でアーケード型カートレースを行う。
- 特徴：爆弾とカラーペイントが車両だけでなく、道路・建物外装・街路設備にも作用する。破壊で形状と衝突判定が変わり、塗装が表面と破片に残る。
- 完成品：実データを使った街で、初回導入からレース開始、3周、結果表示、再レースまで遊べるビルド。レースとは別に自由走行も提供する。

「マリオカートのような」は分かりやすいアーケードレースという体験上の参考であり、既存作品のキャラクター・名称・UI・音楽・音声・モデル・アイテム意匠の複製を指示していない。独自制作する。

### 作業開始のための暫定初期値

岐阜駅北口・信長ゆめ広場周辺、地上中心、PCブラウザー、プレイヤー1台＋AI5台、爆弾とペイント、街路設備と一部建物外装の破壊、昼・晴天、レースと自由走行を初期値とする。約0.3〜0.5km²、周長1.0〜1.5km、3周約3〜5分は未計測の調整目標として保持する。

これらを「ユーザー承認済み」「実測済み」と記録しない。現実の接続を確認できないデッキは走行区間にしない。基準時点は素材ごとの原典年月を調べ、不明なら不明と記録する。根拠なく現在の街を再現したと称しない。

不明点だけを理由に全作業を止めず、可逆な実装判断は理由を記録して進める。ただし、舞台変更、台数削減、ネイティブ専用化、精度・破壊・性能要件の緩和など、体験や受入範囲を変える判断を無断で確定しない。代替案を検証しても、元要件の未達は残す。

初版の対象外は、オンライン対戦、全日本の連続走行、建物内、全建物の全壊、地面掘削、一般交通・歩行者シミュレーションとする。これは原要件の除外範囲であり、その代わりに指定された初版の機能を省略しない。

## 4. 正確な街を作るための実データ処理

### 4.1 収集と出典

`sources.json`を入口に、原本の配布元と利用条件を再確認する。URLや過去の調査記録があることは、データ取得・利用許諾・精度検証の完了を意味しない。

候補区域のCityGML、テクスチャ、README、原典資料、仕様書、索引図を取得し、国土地理院等の道路・地形、利用可能な点群、許諾済みの写真・寸法資料で補う。大容量取得前に容量を確認し、元データをブラウザー配信物やGitに丸ごと入れない。

元ファイルは不変で保存し、SHA-256、取得日、URL、提供者、ライセンス、帰属表示、第三者権利、対象範囲、座標系、高さ基準、原典年月、加工履歴を記録する。公開年度・測量年・撮影年・変換日を区別する。

取得済み／変換済み／表示確認済み／精度検証済みを分ける。ダウンロード失敗を架空データで成功扱いにしない。Google Maps／Earthのメッシュ抽出やStreet Viewの無断大量取得を代替手段にしない。

広告・ロゴ・掲示作品・人物・ナンバーなどは別途点検し、必要なら除去・置換する。実在施設・自治体の公式ゲームと誤認させない。権利や撮影手続の判断は採用時の条件を確認して記録する。

### 4.2 座標・形状・精度

1単位＝1mとし、元座標系からメートル単位のローカル座標への変換、原点、軸、高さ基準を記録・テストする。緯度経度をそのまま距離として扱わない。建物だけでなく、道路、歩道、縁石、広場、橋、デッキの上下関係と衝突面を確認する。

現実にない道路、坂、柱、設備を実在物として捏造しない。レース用バリケードや仮設ランプは `game_added` として分離する。遊びやすくするための道路の無断拡幅・地形移動をしない。

原要件どおり、道路端は概ね±30cm、重要段差・相対路面高さは±5〜10cmを目標に10断面以上、主要建物は検証点で概ね±1mを目標に20地点以上を照合する。参照値、測定方法、誤差、参照資料自体の不確かさを残す。同一データを自分自身と比較して精度検証にしない。

実測や十分な独立資料がない領域は `source_only` または `inferred` とし、`survey_verified` にしない。都市モデルのLODと描画軽量化LODを区別する。

現地に行けない場合は、必要な写真、位置、方向、寸法、許諾を地物ID付きの収集リストにする。別の作業は進めるが、未測量部分の精度要件は未検証として残す。

### 4.3 加工パイプライン

原典取得→区域切り出し→座標変換→補修→区画・物体・表面への分割→表示モデル／衝突モデル／破壊部品／塗装面／経路グラフの生成を、再実行可能なコマンドにする。

元の `gml:id` と `object_id`、`surface_id`、区画IDの対応を維持する。メッシュ統合や軽量化をしても出典と表面へ逆引きできるようにする。道路を含めて単なる巨大一枚メッシュへ潰さない。

## 5. 実装するレース体験

Three.js＋Rapierはブラウザー版の初期候補とし、WebGL2を基準に検討する。既存構成や検証結果によって別案を使う場合は、要件への適合と再現性を説明する。技術名を採用したこと自体を要件達成としない。

ゲームは、タイトル→モード選択→読み込み→短い初回体験→スタート→レース→結果→再レース／自由走行まで接続する。初回体験では、走る・曲がる・ドリフト・構える・投げる・復帰を実際に操作させ、再実行とスキップを可能にする。

キーボードとゲームパッドの両方で、加速、ブレーキ、操舵、ドリフト、照準・投擲、復帰を操作できるようにする。割り当ては画面で確認できるようにし、接続切替、フォーカス喪失、一時停止を扱う。

ドリフト成功は視覚・音・加速で分かるようにする。カメラは進行方向を読めて、壁の中や地面の下へ入り込まず、過剰な揺れや急転で運転を妨げない。壁への吸着、頻発する横転、段差での長時間スタックを修正する。

速度、順位、周回、ミニマップ、アイテム、次の進行方向を表示し、実際のレース状態に接続する。チェックポイントと周回順序を管理し、逆走・コース横断・復帰で順位や周回を不正に稼げないようにする。

AI5台も同じコースと環境効果のルールに従う。壁や破片を無視した座標移動で競走を偽装しない。追い抜き、障害物、ペイント、開いた近道に対応し、想定破壊状態でも完走できるようにする。

落下・逆走・スタックは安全な場所へ復帰できるようにし、指定テストでは3秒以内を目標にする。復帰時に障害物や他車へ重ならず、進行状況を不当に進めない。

実在する幅員のままレースが成立するかを走って確認する。最速経路だけでなく、ドリフト区間、アイテムの駆け引き、破壊で変わる経路を作る。周長・所要時間は実測して記録する。

## 6. 爆弾とペイント：省略不可の中核

### 爆弾

拾う→構える→狙う→投げる→接触・起爆→車両と環境への作用を通す。投擲、効果範囲、起爆条件、調整値を文書化し、壁による遮蔽を判定する。

柵・ベンチ・小物、および一部建物の窓・外装パネル・庇を実際に分離・損傷させる。エフェクト表示や物体の単純消去だけで完成にしない。破壊後は元の衝突判定を除去・更新し、破片は短時間カートや地面と衝突する。

最低1か所、破壊によって近道が本当に開くようにする。一方、主要経路をすべて失わせず、破片でも恒久的に塞がない。破片上限を超えたときは小片の物理を減らし、通路開通という遊びの結果を維持する。

強度・破片・吹き飛びはゲーム調整値であり、現実の構造性能や実際の爆発・倒壊を再現したものと扱わない。

### ペイント

着弾点と表面に沿って局所的な塗装を残す。物体全体の単色化、一定時間で消えるパーティクル、背景へ貼るだけの演出で代用しない。

斜面、縁、重ね塗り、異色の重なりを扱い、壁の裏、別階、別建物へ無条件に貫通させない。飛沫が隣接物へ届く場合も、個々の可視性・命中を判定する。

塗装した柵・外装を壊すと、その位置の塗装が対応する破片に付いたまま移動するようにする。物体ローカル座標やUV／面IDと破片の対応を保持し、分割前後で塗装の位置が不自然に変わらないようにする。

路面には短時間のグリップ変化を実装案として採用し、塗装の見た目の寿命とは分けて管理する。自車と他車で原則同じルールを適用し、範囲・有効時間を伝える。色だけでなく模様・アイコンも使う。

### 状態の維持とリセット

不変の地理モデルと、レースごとの破壊・塗装状態を分離する。区画を描画から外しても、物体ID・表面IDに結び付いた状態は保持する。再読込時に元の柵や当たり判定を復活させない。

1周後・区画再読込後も変化を保持し、新レースでは破片、塗装、グリップ効果、衝突判定、アイテム、AI、順位・周回を整合的に初期化する。

**最優先の中核試験：柵に青いペイントを投げる→爆弾で壊す→青い塗装が破片に付いて飛ぶ→元の柵位置を走り抜ける→一周して戻っても状態が残る→再レースで元に戻る。**

この一連の操作を、映像だけでなく実際の物理・状態変化で成立させる。

## 7. 性能と配信

対象GPU、OS、ブラウザー、解像度、ビルド、計測方法を固定・記録し、1920×1080・60fpsを目標にする。6台、同時爆発3回、近傍の動的破片最大100個、塗装イベント累計200回を実際に再現して負荷試験する。

合否に使うフレーム時間・メモリ・読み込みの予算は計測前に文書化する。平均FPSだけでなくp50／p95／p99、停止や読み込みの長いフレーム、メモリ推移、試験時間を残す。測定後に都合よく閾値を変えない。

通常走行、集団走行、爆発集中、塗装累積、区画境界、3周と再レースの反復を測定する。軽量な人工シーンだけの結果を実ステージの性能にしない。

表示・衝突・状態を区画単位で管理し、データを圧縮・キャッシュ・段階読み込みする。読み込みの進捗、失敗、再試行を画面で扱い、真っ白な画面で停止させない。

CIのheadlessやソフトウェアGPUは機能確認と分ける。対象実機で未測定ならAT-12は未検証とし、「1080p 60fps達成」と書かない。品質を下げた参考結果は別条件として記録する。

## 8. 実行順序と判断ゲート

### Gate A：実在データを使える状態にする
100〜200mの実在区間と広場を切り出す。地上視点で路面・段差・建物低層部・テクスチャ・上下関係・権利を確認する。AOI、プレビュー、出典台帳、欠損・補修計画を残す。

### Gate B：短区間で運転・破壊・塗装を統合する
実データの中で中核試験AT-04を通し、操作、当たり判定の更新、塗装付き破片、状態保持、負荷を確認する。

### Gate C：レース全体を完成させる
1周回、6台、3周、ドリフト、順位、経路案内、復帰、近道、導入、結果、再レースを接続し、最初から最後まで実際にプレイする。

### Gate D：地理精度・体験・公開品質を検証する
近景と数値精度、初見操作、権利表示、性能、再読込・リセット・エラー回復を検証し、受入結果と配布ビルドを作る。

短区間の完成は中間成果であり、ステージ完成ではない。ゲートの未達を隠して合格にしない。ただし外部資料や実機待ちがあっても、依存しない実装・検証は継続する。

## 9. テストと証跡

原要件のAT-01〜13をすべて実行対象にし、対応するGEO／GAME／DEST／PAINT要件と結び付ける。テストを弱めたり、対象から外したりして緑にしない。

- 単体・統合：座標変換、周回・順位、復帰、遮蔽、衝突判定更新、塗装面の選択、破片への塗装継承、区画再読込、新レース初期化。
- 実ブラウザーのE2E：起動、導入、運転、アイテム取得と投擲、中核試験、3周、結果、再レース、自由走行、エラー回復。
- 実データ・実機：10断面以上・20地点以上の照合、立体交差、指定負荷、キーボードと実ゲームパッド、長時間・反復プレイ。

テストごとに、要件ID、条件、手順、期待値、実測値、合否、日時、コミット、環境、ログ・画像・動画・計測ファイルのパスを残す。乱数シードや入力記録を使う場合は、再現範囲も明記する。

画面比較は固定カメラと参照位置を対応させる。状態テストは実際の描画・物理系とも照合し、テスト用変数だけを書き換えて成功にしない。スクリーンショットは物理や性能の証明として単独使用しない。

操作テストでは、進行方向、ドリフト、照準、復帰が初見で理解できたか、迷いや誤操作を記録する。AIによる操作、スクリプト操作、人の初見プレイを明確に分ける。人がいないのに「人が確認した」「初見で面白いと評価した」と書かない。

複数エージェントを実際に利用できる場合は、地理・物理／状態・UI／走行・QAを分担し、相互レビューする。利用できなければ視点を分けて順番にレビューし、独立エージェントが検証したと称さない。

## 10. 要件台帳と完成判定

各要件を1行ずつ記録し、最低限、原文／出典、受入条件、実装箇所、テストID、証跡、状態、未達理由、次の作業を持たせる。

状態は `NOT_STARTED`、`IN_PROGRESS`、`PASS`、`FAIL`、`BLOCKED`、`NEEDS_DECISION`を使う。「実装済み」と「検証して合格」は区別する。未実行・スキップ・資料不足はPASSにしない。明示的な合意なく要件を対象外にしない。

総合完了と報告できるのは、合意された受入範囲の全必須要件とATがPASSになり、対応する証跡と実行可能なビルドがある場合だけ。要件を変更した場合は元要件との差を示し、変更後の達成を元要件そのままの完全達成と呼ばない。

精度検証、対象実機測定、必要な権利確認などが未完了でも、動くビルドと実施済みの証跡を提出する。その際は「プレイ可能・受入未完了」のように区別し、残った要件ID・理由・解消に必要な資料や作業を明示する。

## 3. 材料の収集計画

### 3.1 PLATEAUを骨格にする

候補区域のCityGML、テクスチャ、README、原典資料リスト、拡張製品仕様書、索引図を同時に取得する。閲覧確認には3D Tiles、地物分割と編集にはCityGMLを使う設計とする。

岐阜市2024年度版の公開圧縮サイズはCityGML約4.3GB、3D Tiles/MVT約3.6GB。これは配布元データであり、ブラウザーにそのまま配信する容量ではない。[S01]

取得した元ファイルは変更せず保管し、SHA-256、出典、取得日、ライセンスの版を記録する。範囲を切り出してから加工し、元の gml:id とゲーム object_id の対応を保持する。

### 3.2 地形・道路を公的データで照合する

国土地理院の基盤地図情報では道路縁・建築物外周線等と数値標高モデルを扱える。DEMの1m・5m・10mという値は格子間隔であり、それだけでモデルの誤差を保証する値ではない。[S10]

ゲーム内の道路面、橋の上下関係、敷地境界付近を優先して照合する。地形上面だけで橋の上と下を一枚の面にしない。航空写真は路面と屋根の補足候補であり、低い目線の壁面を代用できると考えない。

### 3.3 点群と現地の写真・寸法で近景を補う

静岡県のVIRTUAL SHIZUOKAは公開点群の収集先候補。県の案内はCC BY 4.0を明示するが、選択するデータの範囲・撮影年・点密度・計測方式を個別に確認する。[S07]

現地調査は、全街区の全面スキャンではなく、走行線周辺の縁石、傾斜、入口、柵、支柱、ベンチ、建物低層部を優先する。両側からの連続写真、角を回り込む写真、寸法確認用写真、標準視点の比較写真を分けて記録する。動く人・車・ガラスの反射に隠れた箇所は未確認として残す。

写真ごとに撮影日、撮影位置、向き、対象ID、撮影者と利用権限、測った寸法を記録する。写真だけから高精度の絶対位置を保証しない。必要に応じて公共資料や測量値で拘束する。

撮影方法と場所に応じて管理者のルールを確認する。初版は地上からの収集を中心にし、ドローンは必須にしない。採用する場合は機体・空域・運航方法に応じた許可承認等を別途確認する。[S20]

### 3.4 図面・BIM・OSMは用途を限定する

自治体や管理者の図面・BIMは、利用条件と「計画図か竣工図か」を確認してから使う。古い計画図の寸法を現在の実測値にしない。

OpenStreetMapは経路の接続や名称の補助候補とする。ODbLの帰属表示とデータベースに関する条件を確認し、出典が追えるように分離管理する。[S13]

## 4. 権利・出典管理

PLATEAUの公開データは商用を含む利用を想定するが、適用条件はデータセットごとに確かめる。[S01][S14]

国土地理院のデータは出典と加工の表示を管理し、取得形態・用途に応じて測量成果の複製・使用手続の要否を確認する。「常にクレジットだけでよい」と扱わない。[S11][S12]

Google Maps Platformの規約には外部利用のための抽出・スクレイピングやGoogle Mapsコンテンツからの新たなコンテンツ作成への制限がある。Google Earth/Mapsのメッシュ抽出やStreet View画像の大量取得を制作基盤にしない。APIで表示する許諾と、モデルやテクスチャを加工して配布する許諾を分けて考える。[S15]

広告、企業ロゴ、掲示作品、第三者写真などは地理データ本体と分けて点検する。人物やナンバー等の写り込みは制作素材から除去・置換する方針とする。ゲームは実在施設や自治体の公式作品と誤認されない表示にする。カート、キャラクター、UI、音楽、アイテム表現は独自制作とする。

## 9. モデルの分離と実装案

```text
公開CityGML / 公的地形 / 点群 / 許諾済み写真
  → 原典保管・ライセンス台帳・範囲/年月照合
  → 座標変換・走行部分の補修
  → 元地物IDを保持して物体/表面/区画に分割
  → GLB等の表示モデル + 静的衝突モデル + 破壊部品
  → 塗装用UV/面ID + 経路グラフ + 出典メタデータ
  → レース実行時の破壊・塗装状態
```

表示用の街を一枚の巨大メッシュにまとめず、少なくとも道路・建物・壁面・破壊設備の識別を保持する。描画最適化をする場合も、元の地物・表面への逆引きを残す。

オフライン加工はPLATEAU SDKとBlender等を組み合わせる案とする。PLATEAU SDK for UnityはFBX/OBJ/glTFへの出力を案内している。[S17]

ブラウザー案はThree.js + Rapier。初版はWebGL2対応を基準にし、必要に応じてWebGPUを検証する。Three.jsにはデカール用機能があり、Rapierには静的形状と動的剛体の衝突形状を選択する機能がある。[S18][S19]

道路は静的な衝突用三角形メッシュ、破片は単純形状または凸形状を基本案とする。塗装は初期検証にデカールを使い、件数増加に対応する面単位の描画先テクスチャ・記録方式を検証する。塗装済み表面と破片のUV対応を事前に持つ。これは実装設計案であり、都市モデルを読み込むだけで自動実現される機能ではない。

## 10. 性能目標と測定

対象PCのGPU・ブラウザー・解像度を固定してから評価する。以下は初期予算であり、達成済み値ではない。

| 項目 | 提案目標 |
|---|---|
| 描画 | 1920×1080で60fpsを目標。通常時と負荷時のフレーム時間を記録 |
| 負荷試験 | 6台、同時爆発3回、近傍の動的破片最大100個、塗装イベント累計200回 |
| 破片の上限超過 | 小片を非衝突の見た目に落とす。核心となる通路開通は維持 |
| 配信 | 都市全域のZIPを配信しない。区画単位のGLB・テクスチャを読み込む |
| 状態管理 | 描画区画の解放と、破壊・塗装状態の保存を切り離す |
| 調整手順 | 解像度・近景詳細・動的破片数を調整し、必要ならPCネイティブ案へ移る |

## 11. 受入試験

| ID | 試験 | 合格条件 |
|---|---|---|
| AT-01 | 都市モデル確認 | 仮の箱街ではなく、採用地区の道路形状・主要建物・地上階の特徴が資料と対応する |
| AT-02 | 基準点・断面比較 | GEO-04/05の指定検証点で数値を測り、未達を台帳に残す |
| AT-03 | 上下関係 | デッキ上と地上の衝突・塗装・経路を混同しない |
| AT-04 | 柵を塗って壊す | 塗装が破片と共に移動し、元の柵位置を走行できる |
| AT-05 | 壁を塗る | 反対側の面と別階に塗装が漏れない |
| AT-06 | 走行中の破壊 | 破片に反応しつつカートが長時間操作不能にならない |
| AT-07 | 周回継続 | 1周後も破壊と塗装が残り、2周目の見た目と攻略に反映される |
| AT-08 | 区画再読込 | 画面外から戻っても破壊・塗装が復元される |
| AT-09 | 完走可能性 | 想定破壊状態で全AIとプレイヤーに有効な完走経路がある |
| AT-10 | 初見操作 | 操作説明を読まずに始めた検証者にも、進行方向・アイテム使用・復帰方法が分かるか記録する |
| AT-11 | リセット | 再レースで元の街に戻り、前レースの当たり判定・塗装が混ざらない |
| AT-12 | 性能 | 指定負荷でフレーム時間・メモリ・読み込みを測定し、対象機の合格予算内に収める |
| AT-13 | 出典 | 同梱する全素材を出典・条件・改変履歴へ追跡できる |

## 12. 制作順と判断ゲート

### Gate A: 候補地区のデータが使えるか

100〜200m程度の実在区間と広場を切り出す。地上カメラで見て、テクスチャ・路面・段差・上下関係・地物ID・ライセンスを確認する。駅北口の必要部分が不足する場合は、追加取得の手間を見積もってから範囲または候補地を変更する。

成果物: AOI、出典台帳、モデルプレビュー、欠損一覧、補修見積り。

### Gate B: 環境に干渉する遊びが成立するか

短い実在区間で、走行、爆弾、ペイント、実際の当たり判定更新、塗装済み破片を通す。AT-04を最優先に実施する。

成果物: 操作可能な短区間、テスト記録、負荷計測。

### Gate C: レースとして成立するか

地上の1周回を作り、6台、ドリフト、経路案内、順位、復帰、ショートカット、3周の状態維持を実装する。狭すぎる区間は勝手に拡幅せず、近道化・経路変更・台数変更を検討する。

成果物: 最初から最後まで遊べるレース、初見プレイ評価。

### Gate D: 精度と公開品質を仕上げる

走行周辺に限って写真・実測で補修し、近景の照合、権利表示、性能、クラッシュ復帰を検証する。

成果物: 受入試験結果、既知の制約、公開用ビルド。

## 13. 未確定事項

2. 初版の破壊を街路設備と一部外装に限定してよいか。全建物崩壊が必須なら先に実装・性能計画を変更する。
3. 地理の基準時点を公開データ当時にするか、現地調査で更新するか。
4. 現地写真・寸法確認に使える時間と予算。
5. 岐阜駅北口の実データを見た後の正確なAOI、ルート、デッキ利用可否。
